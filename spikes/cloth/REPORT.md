# 布たたみ 実現性検証スパイク — 報告

実施: 2026-11-13（1 セッション）。設計図は `~/Downloads/KeiArm_Cloth_Spike_Handoff.md`（以下「設計図」）。
E3 のロボットは利用者の決定どおり OpenArm v2（両腕）を使った。既存のシミュレーター・方策・ブラウザのコードと
`third_party/` は変更していない（検証コードは全て `spikes/cloth/`）。

## 判定: **D（Python の速度が足りない）**。ブラウザは B の制約（実時間で描けない）も重なる

- **層は破綻しない。** E2 の安全な 4 設定 × 100 回 = 400 回で破綻 0 回、層のすり抜け（布の中心面の交差）0 回。E3（双腕）の 60 回も破綻 0 回（E3 ではすり抜けの判定は測っていない）
- **二つ折りは合格。** 四つ折りは「すり抜けなし」だが、決め打ちの軌道では掴んだ角の付近がめくれ、層の順序の違反が 6〜19% 残る（設計図 5 章の「違反ほぼ 0」は満たさない）
- **速度が判定を決める。** 品質が一番よい設定（候補 A、N = 16）は双腕 + 布の物理だけで **実時間の 0.57 倍**。実時間を超えるのは、メッシュを粗くするか（N = 10 で 1.8 倍）、拘束をやめて弾性で持たせるか（候補 B、N = 16 で 1.16 倍）のどちらかで、どちらも 3 倍の余裕はなく、品質も落ちる
  - ソルバーの反復を減らして速くすると（B、N = 10、反復 10 で 4 倍）**層がすり抜け、机も突き抜ける**（100 回中 16 回破綻）
- **ブラウザは同じ挙動で動くが遅い。** WASM の物理は Python の約 1.6〜1.7 倍遅い。N = 10 でも物理がほぼ実時間で 14 fps、N = 16 は実時間の 0.2〜0.3 倍
- **掴みの簡略化（閉じたら頂点を拘束）は実装できた。** 拘束スロットの相手（`eq_obj2id`）と anchor（`eq_data`）を実行時に書き換える方式が Python・JS の両方で動く
- 一方で **データ収集の総量は並列で足りる見込み**（12 コア機で 10 並列にすると、候補 A・N = 16 でも二つ折り 1 エピソード約 74 秒、1 時間に約 490 本。下の「収集の見積もり」）

## 1. 4 つの問い（設計図 1 章）への答え

| 問い | 答え |
|---|---|
| 1. 二つ折り・四つ折りで層が安定して重なるか | **二つ折り: はい。** 候補 A（N = 16）の 100 回で違反頂点 0%、すり抜け 0、離した 2 秒後も形が保たれる（面積比 0.474、角の距離 18 → 19 mm）。**四つ折り: すり抜けはないが、形は甘い。** 400 回ですり抜け 0。違反は 6〜19%（A・N = 16 で平均 7.9%）、角の距離は離して 2 秒後の平均で 48〜77 mm。違反は掴んだ角の付近に集中し、「掴んだ点は向きを変えずに運ばれ、間の布が 180° 裏返る」ことによるめくれ（下の 2.3） |
| 2. 速度はデータ収集に使える水準か | **単一プロセスの実時間比は足りない。** 双腕 + 布（二つ折り、物理のみ）: A・N = 16 で 0.57 倍、A・N = 10 で 1.8 倍、B・N = 16 で 1.16 倍（剛体の棒タスクは 67.8 倍）。四つ折り（層が 4 枚）はさらに遅い（布単体で A・N = 16 が 0.30 倍）。**並列にすれば収集の総量は足りる**（2.5） |
| 3. ブラウザ（MuJoCo WASM）で動き、three.js で描けるか | **動く・描ける・挙動も揃う。** 固定版 `@mujoco/mujoco` 3.17.0（単一スレッド版）で同じ XML が読め、`flexvert_xpos` から `BufferGeometry` を毎フレーム更新して両面描画（表は格子、裏は単色）できた。Python との差は二つ折りの角の距離で 0.2 mm 以内。**ただし実時間 + 30 fps には届かない**（N = 10 で物理が実時間ちょうど・14 fps） |
| 4. 「閉じたら頂点を拘束」の簡略化は実装できるか | **できる。** 頂点ごとにボディ（`cloth_k`）ができるので `equality/connect` を張れる。手ごとに非アクティブの拘束スロット 4 本を事前に定義し、掴む瞬間に `eq_obj2id`（相手ボディ）と `eq_data`（anchor）を書き換えて `eq_active` を立てる方式が、Python と JS の両方で期待どおり動いた（E3 の 60 回で毎回、N = 16 は 4 頂点、N = 10 は 3 頂点を掴み、拘束の誤差は最大 4.1 mm） |

## 2. 実験ごとの結果

### 2.0 E0: 環境確認（`e0_env.py`、メモは `NOTES.md`）

- 固定版 3.17.0 に `mjEQ_FLEXVERT`、`elastic2d`、`flexvert_xpos` があり、**バージョンを上げる必要はない**（設計図 2.2 の手順は不要）。npm 側も同じ 3.17.0
- `poncho.xml`（3.17.0 タグ）と同じ flexcomp 設定を球にかぶせて動かした: `out/e0_poncho_like.mp4`
- リファレンスの要点と、実際に動かして分かった制約は `NOTES.md`。特に影響が大きいもの:
  - **flex の elasticity を使うと `integrator="discrete"` が必須**（implicitfast はコンパイルエラー）
  - edge の等式拘束と `young` は `elastic2d="bend"` のときだけ併用できる
  - 2D の grid では `dof="trilinear"` / `"quadratic"` がコンパイルできない

### 2.1 E1: 布だけを落とす（`e1_drop.py`、表は `out/e1_table.md`）

机の上に、-x 側の 1/3 を高さ 4 cm の箱にかけて落とし、2 秒で静止させた。基準は 24 cm 角・20 g・radius 2 mm・CG・1/240 s。
全 50 条件のうち、`selfcollide="narrow"` の N = 24、32（スタック不足）以外は破綻なし。実時間比（他の処理を止めて測り直した値）は、箱にかかる接触が多いこの試験で N = 10 が 2.7〜3.5 倍、N = 16 が 0.9〜1.2 倍、N = 24 が 0.3〜0.6 倍、N = 32 が 0.1〜0.3 倍。

| 比べたもの | 分かったこと |
|---|---|
| 伸びの拘束 `edge equality` | **`vert` は使えない**: 箱の縁で布がゴムのように伸びる（辺の最大伸び 94〜300%、`out/e1_snap_vert.png`）。**`true`** は伸び 2〜17%（N が大きいほど伸びる: p95 で N = 16 が 3.4%、N = 32 が 9.4%）。**`false` + `elastic2d="both"`（young 2e5）** は伸び 0.5% 以下で拘束の行が少なく速い |
| 曲げ `elastic2d`、`young`、`thickness`、`poisson`、`damping` | 形はこの落下試験では差がほとんど出なかった（垂れ方・弾みとも同じ）。曲げ剛性の効きは今回は確かめきれていない（未解決 5.1）。**速さは曲げで大きく変わる**: N = 16 で曲げあり 0.93 倍、曲げなし（`elastic2d="none"`）1.79 倍 |
| `radius` | 層の厚み（静止時の高さ = radius）。1〜4 mm で破綻なし |
| 自己衝突 | `auto` は 2D では `sap` と同じ（接触数も一致）。`sap` が最速、`bvh` がその次、`narrow` は N = 24 以上でスタック不足 |
| 時間刻み、ソルバー | CG が Newton より速い（この試験で 1.5〜2 倍、層が重なった状態では 2.5〜9 倍）。1/120 s でも布単体は破綻しない（N = 16 で 1.6 倍速） |
| 机の形 | **箱だと三角形ごとに約 3 点の接触**（N = 16 で 1350 点）、平面なら頂点ごとに 1 点（256 点）。平面にすると布単体の物理が 2.5 倍速い。以降は布専用の衝突平面を使った |
| `dof="trilinear"` / `"quadratic"` | 2D の grid ではコンパイルできず（`flex grid rotation R0 is not orthonormal`）、試せなかった |

候補設定として、**A: `edge equality="true"` + `elastic2d="bend"`**（品質）と **B: 拘束なし + `elastic2d="both"`、young 2e5**（速さ）を選んで E2 へ進んだ。

### 2.2 E2: スクリプトでたたむ（`e2_fold.py`、最重要）

24 cm 角の布の角を mocap 2 個に connect でつなぎ、弧で運んで離す。二つ折り（x の遠い辺を近い辺へ）→ 続けて四つ折り（+y 側を -y 側へ、2 層の角を掴む）。
試行ごとに布の位置（±2 cm）と向き（±10°）、軌道の所要時間（1.5〜3 秒）と持ち上げ高さを乱数で変えた。各 100 回。
動画: `out/e2_fold_n16_seed0_side.mp4`、`out/e2_fold_n16_seed0_top.mp4`（コマ送りは `out/e2_strip_side.png`、`out/e2_strip_top.png`）。

指標:
- 違反: 上層の頂点が、対応する下層の頂点より下にある割合（全ての重なりの組で数える）
- すり抜け: 布の中心面の交差の数（辺が、頂点を共有しない三角形を貫く数）。0 なら層は物理的にすり抜けていない
- 面積比: 上から見た凸包の面積 ÷ 元の面積（理想は二つ折り 0.5、四つ折り 0.25）
- 角の距離: 重ねた角どうしの距離

| 設定（各 100 回） | 破綻 | 二つ折り 違反（平均 / 最大） | 二つ折り 面積比（直後 / 2 秒後） | 二つ折り 角の距離 [mm] | 四つ折り すり抜けた試行 | 四つ折り 違反（平均 / 最大） | 四つ折り 面積比（直後 / 2 秒後） | 四つ折り 角の距離 2 秒後 [mm]（> 100 mm の回数） |
|---|---|---|---|---|---|---|---|---|
| **A N = 16** | 0 | **0 / 0** | 0.474 / 0.474 | 18 / 19 | **0** | 7.9% / 11.5% | 0.237 / 0.249 | 48（0） |
| B N = 16 | 0 | 0.9% / 6.3% | 0.467 / 0.468 | 19 / 20 | 0 | 6.0% / 11.5% | 0.265 / 0.281 | 56（9） |
| A N = 10 | 0 | 2.8% / 8% | 0.552 / 0.555 | 26 / 28 | 0 | 15.8% / 17.3% | 0.273 / 0.273 | 56（0） |
| B N = 10 | 0 | 9.1% / 20% | 0.555 / 0.556 | 29 / 28 | 0 | 18.9% / 29.3% | 0.304 / 0.308 | 77（40） |
| B N = 10、反復 10 | **16**（机を突き抜け） | 5.3% / 14% | 0.557 / 0.556 | 28 / 28 | **18** | 35.7% / 60% | 0.451 / 0.478 | 184（60） |
| B N = 10、反復 10、自己接触 condim 1 | 0 | 5.7% / 14% | 0.558 / 0.558 | 29 / 29 | **16** | 30.0% / 48% | 0.389 / 0.427 | 146（54） |

- 二つ折りの違反は、どの設定でもすり抜けではない（すり抜け 0）。N = 10 の違反は、粗い格子で折り目が 1 マス（2.7 cm）分の輪になり、端がめくれることによる。N = 10 の面積比が 0.55 なのも同じ理由
- **四つ折りの違反の原因**（seed 0〜3 で調べた）: 違反は掴んだ角（2 層を一緒に掴んだ方）の近くの縁に集まっていて、上下の差は最大 10 mm。すり抜けは 0。掴んだ点は向きを変えずに運ばれるので、掴んだ所では 2 層の上下が元のままになり、その間の布が 180° 裏返って巻く（めくれ）。層の対応を「理想的に裏返った」前提で数えているので、これが違反として出る。掴んだ点を折り目の軸まわりに 180° 回しながら運ぶと悪化した（試行 2 回で二つ折りにも違反 4.7%）ので、回転では直らない。折り方（掴む位置、軌道）を工夫する余地は残っている
- **候補 B の注意**: 掴んだ瞬間に `Flex stiffness is too ill-conditioned for the effective-metric block preconditioner` の警告が出る（破綻はしない）。WASM との差も B の方が大きい（2.6）
- 判定基準（設計図 5 章）との対応: 安定性（100 回で破綻 0）は A・B とも合格。層の重なりは二つ折りが A・N = 16 で合格、四つ折りは不合格（すり抜けではなく形）。形の保持は二つ折りで合格（2 秒で面積比も角の距離もほぼ変わらない）

### 2.3 E3: ロボット（OpenArm v2）との連成（`e3_robot_fold.py`、`e3_integrator.py`）

既存の双腕シーン（`keiarm/openarm/scene.py` の `build_spec`）から棒と皿を除き、20 cm 角の布を置いた。両手が布の遠い角を掴み、
IK の決め打ち軌道（弧）で近い角の上へ運んで離す（二つ折り 1 回）。

- **布の大きさ 20 cm**: 右手が y = -0.10、左手が y = +0.10 の線上で x = 0.125〜0.30 を往復する。これが真下向きの把持で両手とも届く範囲（`docs/openarm/reach_cube.json` と IK で確認）。**顎の向きは自然な向き（`HOME_YAW`）から 60° 回した**: 自然な向きのままだと x < 0.2 で IK が解けない。拘束で掴むので顎の向きは布に関係しない
- **積分器**: 布の曲げに `discrete` が必須なので、ロボットも `discrete` で動かす。既存の決め打ち把持を両方の積分器で比べ、結果は同じだった（持ち上げ 147 mm、追従誤差 9〜12 mm、`out/e3_integrator.json`）
- **衝突のビット**: 机の箱は contype 4 / conaffinity 1（アームとだけ当たる）、布は contype 2 / conaffinity 3（アーム、布専用の平面、自分自身と当たる）、布専用の平面は contype 2 / conaffinity 2
- 動画: `out/e3_weld_n16_seed0_{side,top,cam_front}.mp4`（コマ送り `out/e3_strip_side.png`、`out/e3_strip_top.png`）

| 設定（各 20 回、10 並列） | 完了 | 掴んだ頂点（左右） | 拘束の誤差 最大 [mm] | 違反（平均 / 最大） | 面積比 | 角の距離 平均（範囲）[mm] | アームと布の接触ステップ |
|---|---|---|---|---|---|---|---|
| **A N = 16** | 20/20 | 4 / 4 | 1.9 | 1.4% / 3.1% | 0.471 | 39（18〜53） | 6 |
| B N = 16 | 20/20 | 4 / 4 | 4.1 | 7.3% / 12.5% | 0.533 | 25（15〜48） | 24 |
| A N = 10 | 20/20 | 3 / 3 | 3.6 | 14% / 20% | 0.446 | 23（9〜59） | 6 |

- 掴む・運ぶ・離すは全て破綻なく通った。アームと布の接触（指が布に触れる）でも巻き込みや破綻は起きなかった
- 角の距離が E2 より大きいのは、IK の目標（弧）に手が最大 80 mm 遅れるため（運ぶ 2.5 秒が速すぎる）。軌道の調整で縮むはず
- **摩擦だけで挟む方式**（1 回だけ、`--friction`）: 指先を机の 2 mm 下まで押し付けて閉じると、布の角を挟んで持ち上げられた。二つ折りにはなったが違反 19.5%、角の距離 37 mm と荒い（拘束方式は同じ試行で 0.8%、19.5 mm）。指を机に押し付ける動作が前提になるので深追いしなかった（`out/e3_friction_n16_seed0_side.mp4`）

### 2.4 E4: Python 側の描画（`e4_render.py`、`out/e4_render.png`）

- `mujoco.Renderer` で布が描ける。`material` のテクスチャ（格子）が貼れる（grid は texcoord を自動で作る）
- **表と裏の色は分けられない**（flex の材質は 1 つ）。回避策として、`update_scene` の後に `mjvScene` へ裏面の三角形（`mjGEOM_TRIANGLE`、法線の逆向きに radius だけずらす）を 450 個足すと、裏だけ青で描けた（`out/e4_render.png` の左下）。本実装で使うなら、描画の一致（three.js 側）と速さを確かめる
- **セグメンテーション描画で布は識別できる**（布の画素の objtype が `mjOBJ_FLEX`）
- OpenArm + 布で、既存のカメラ構成（`cam_front` + 両手首、160×120）の描画は 1 制御周期あたり約 1〜3 ms（既存の `scripts/bench_openarm.py` で 0.9 ms、布ありの E4 は並列負荷の下で 2.9 ms）。物理（二つ折りで 1 制御周期 = 物理 8 ステップに 18〜58 ms）に比べて小さい

### 2.5 速度（`bench.py`、単一プロセス、他の処理を止めて実行）

機械: 12 コア、RTX 3060。布単体は E2 の seed 0（二つ折り → 四つ折り、9.45 秒）、双腕 + 布は E3 の seed 0（二つ折り、10.2 秒）。

| 設定 | 布単体: たたむ間 / 静止後 | 双腕 + 布: 物理のみ / IK 込み |
|---|---|---|
| A N = 10 | 1.28 / 1.22 | **1.82** / 1.35 |
| A N = 16 | 0.37 / 0.30 | **0.57** / 0.51 |
| A N = 24 | 0.13 / 0.11 | — |
| B N = 16 | 0.58 / 0.47 | **1.16** / 0.93 |
| B N = 10、反復 10 | 3.94 / 2.72 | 6.5（ただし机を突き抜けて破綻） |
| （参考）既存の棒タスク、剛体のみ | — | 67.8（描画込み 24.2） |

- **遅い理由**: 層が重なると自己接触が約 1000 点（N = 16）になり、CG が既定の 50 反復で収束しないまま毎ステップ上限まで回る。たたんで静止した状態で 1 ステップ 97 ms（並列負荷の下、`diag_fold_speed.py`）。衝突検出と拘束の組み立てだけで 1 ステップ（4.2 ms）を超える。Newton はさらに遅い（850 ms）。PGS は discrete + flex で未対応
- 速くする手: 反復を 10 に減らすと 3〜4 倍速いが、層がすり抜ける（E2）。自己接触を condim 1（摩擦なし）にすると静止状態で約 2 倍。`passive` 接触（実験的、摩擦なし、すり抜けを保証しない）は拘束を解かなくなるが、衝突検出の時間は残る
- **決定性**: 同じ seed を同じプロセスで 2 回回し、時間以外の値が全て一致（布単体 A・B、双腕 + 布 A）

#### 収集の見積もり（二つ折り 1 エピソード = 10.2 秒、描画 3 台込み、エキスパートの計算は含まない）

10 並列の実測値（E3 のバッチの IK 込み実時間比）から:

| 設定 | 1 エピソードの所要（1 プロセス） | 10 並列での 1 時間あたり |
|---|---|---|
| A N = 10 | 約 13 秒 | 約 2,800 本 |
| A N = 16 | 約 74 秒 | 約 490 本 |
| B N = 16 | 約 24 秒 | 約 1,500 本 |

既存のマイルストーンの BC は 1,200 エピソード程度で成功率 100% に届いているので、二つ折りの収集だけなら A・N = 16 でも 3 時間程度で足りる。
四つ折りはエピソードが約 2 倍長く、層が 4 枚で 1 ステップも遅くなるので、1 時間あたりは数分の 1 になる。

### 2.6 E5: ブラウザ（`web/`）

- `web/export_scenes.py`: E2 の布単体シーン（A N = 10 / 16 / 24、B N = 10 / 16、各 3 試行）の XML と試行のパラメータ、同じ試行の Python の結果を `web/scenes/*.json` に書き出す
- `web/fold.mjs`: E2 の手順を JS に写したもの（Node とブラウザで共用）。拘束スロットの差し替えも JS で行う
- `web/node_check.mjs`（Node）、`web/index.html` + `main.mjs`（three.js、両面描画、法線の毎フレーム再計算）、`web/browser_check.py`（ヘッドレス Chrome、実 GPU）
- **JS から `eq_obj2id` / `eq_data` / `eq_active` を書き換えて拘束を切り替えられる。** `flexvert_xpos`、`flex_elem`、`flex_texcoord` も読める

## 3. 推奨パラメータ（MJCF の断片）

二つ折りの品質を優先した候補 A。速度が要る場合の B は下に差分で示す。

```xml
<option timestep="0.004166667" integrator="discrete" solver="CG" iterations="50" cone="pyramidal"/>
<!-- 机: 見た目の箱とは別に、布だけが当たる平面を上面に置く（箱だと接触が約 3 倍） -->
<geom name="cloth_floor" type="plane" size="0.5 0.6 0.01" rgba="0 0 0 0" contype="2" conaffinity="2"/>
<flexcomp name="cloth" type="grid" count="16 16 1" spacing="0.01333 0.01333 0.01333" dim="2"
          radius="0.002" mass="0.02" material="cloth_mat">
  <edge equality="true" damping="0"/>
  <elasticity young="5e3" poisson="0" thickness="1e-3" elastic2d="bend"/>
  <contact selfcollide="sap" contype="2" conaffinity="3" condim="3" friction="0.6 0.005 0.0001" solref="0.01 1"/>
</flexcomp>
<!-- 掴み: 手ごとに 4 本、非アクティブで定義し、実行時に body2（eq_obj2id）と anchor（eq_data）を差し替える -->
<connect name="right_slot0" body1="openarm_right_ee_base_link" body2="cloth_0" anchor="0 0 0" active="false" solref="0.01 1"/>
```

- 20 cm 角（OpenArm の両手が届く範囲）。spacing = 0.20 / (16 - 1)
- 候補 B: `<edge equality="false"/>`、`<elasticity young="2e5" poisson="0" thickness="1e-3" elastic2d="both"/>`。伸びは 0.3% 以下で速いが、二つ折りの違反が E3 で 7%、WASM との差も大きい
- **`iterations` は減らさない**（10 で層がすり抜ける）。`edge equality="vert"` は使わない（伸びる）
- 机の箱は contype 4 / conaffinity 1 にして、布と当てない

## 4. 想定外だったこと

1. **flex の弾性に `integrator="discrete"` が必須**（3.17.0）。OpenArm は implicitfast 前提だったが、discrete でも決め打ち把持は同じ結果だった。ただし既存の剛体タスク（エキスパート・方策）を discrete で回し直したわけではない
2. **`edge equality="vert"`（粗いメッシュ向けの flexvert）が、この用途では伸びすぎて使えない。** 設計図の「粗いメッシュで速く」の当てが外れた
3. **2D の布では `trilinear` / `quadratic` が使えない**
4. 机を箱にすると接触が 3 倍になる。衝突のビットで布専用の平面に逃がす必要がある
5. 速度の律速は布そのものではなく、**層が重なったときの自己接触の拘束を解く時間**。布が平らなうちは速い（N = 16 の布単体が平面上で約 3.5 倍）が、たたむほど遅くなる
6. 四つ折りの違反はすり抜けではなく、掴んだ点が向きを保つことによるめくれ。「層の違反率」は折り方の良し悪しも拾うので、すり抜けの判定（中心面の交差）と分けて見る必要がある
7. 自然な顎の向きでは OpenArm の手前側（x < 0.2）に真下向きで届かない。拘束で掴む前提なら顎の向きは自由に選べる
8. `MjSpec.to_xml()` の XML は `angle="radian"`。そこへ足す flexcomp の `euler` を度で書いて布が 270° 回った（`NOTES.md` 9）

## 5. 未解決の点

1. **曲げ剛性の効き**: E1 の落下試験では young・thickness を 100 倍変えても形が変わらなかった。試験が曲げを測れていない可能性が高い。タオルらしい垂れ方の同定は手付かず（Blanco-Mulero らのパラメータ同定が出発点）
2. **四つ折りの形**: 掴む位置と軌道（2 層の角の掴み方、持ち上げ高さ、置く位置）の調整はしていない。違反の定義も、めくれを許すものに直す余地がある
3. **四つ折りの OpenArm での到達**: 2 回目の折りは手が反対側の手の領域（y の符号が逆）まで運ぶ必要がある。E3 は二つ折りだけ
4. **既存の剛体タスクを discrete で回したときの影響**（エキスパートの成功率、方策の評価）は未確認
5. **マルチスレッド版 WASM**: 試していない。GitHub Pages ではクロスオリジン分離のヘッダを付けられないので、Service Worker でヘッダを足す回避策（coi-serviceworker の方式）の可否を調べる必要がある
6. 双腕 + 布のブラウザでの速度は測っていない
7. 裏面の色の回避策（`mjvScene` に三角形を足す）を、三台のカメラの毎ステップ描画に入れたときの速さ

## 6. 判定後の分岐（設計図 7 章 D）への材料

| 設計図の手 | 結果 |
|---|---|
| `flexvert` を使ったより粗いメッシュ | 使えない（E1: 伸びすぎる） |
| 自己衝突の方式の見直し | `sap` が既に最速。律速は検出ではなく拘束の求解で、反復を減らすと層がすり抜ける |
| 自作の布 | 下の E6 メモ |

今回分かった別の手:
- **並列で収集する**: 1 プロセスが実時間を下回っても、10 並列で二つ折り 490〜2,800 本/時（2.5）。学習には足りる見込み
- **曲げをなくす**（`elastic2d="none"`、edge 拘束だけ）: E1 で 1.9 倍速く、弾性がないので積分器も implicitfast のままでよくなる。たたむ品質（E2）は試していない
- **メッシュを N = 10〜12 にする**: A・N = 10 は双腕 + 布で 1.8 倍。ただし二つ折りの折り目が角ばり、違反が増える（E2 で 2.8%、E3 で 14%）。N = 12 は試していない
- **ブラウザは記録の再生に限る**（設計図 7 章 B の 3 案目）か、ブラウザだけ粗くする（学習と挙動がずれる）

### E6: 自作の布（位置ベースの手法）に切り替える場合に必要になるもの（コードは書いていない）

- **Python と JS の二重実装**: 拘束の投影（距離・曲げ・自己衝突）を同じ順序・同じ反復回数で両方に書く。浮動小数の差はあってよい（現行方針どおりビット一致は求めない）が、手続きの一致はテストで保証する（記録した行動列を両方で再生して最終形状を比べる。今の `npm test` と同じ形）
- **ロボット（MuJoCo）との連成**: 片方向（ロボットが布を押す・掴む、布はロボットに力を返さない）なら簡単。MuJoCo の指・手のジオメトリ（カプセル・メッシュの凸包）を毎ステップ読み、布の頂点を押し出す。掴みは今回と同じく「閉じたら頂点を手の座標に固定」。布の重さがロボットに効かない（20 g なので実害は小さい）
- **自己衝突**: 層の重なりが本題なので一番重い。頂点–三角形の近接を空間ハッシュで探し、厚み（今回の 2 × radius）を保つ投影を入れる。すり抜け防止には連続衝突（前のステップからの移動を見る）が要る。今回の「中心面の交差」の判定がそのまま検査に使える
- **速さの見込み**: 位置ベースの手法は反復回数を固定できるので、1 ステップの時間が層の数で大きく変わらない。WASM でも JS でも、N = 16 の布なら 1 ms 以下を狙える（要検証）
- **失うもの**: MuJoCo の接触・摩擦の扱い（指と布の摩擦把持はできなくなる）、`flexvert_xpos` をそのまま描く手軽さ、MuJoCo の描画とセグメンテーション（布だけ自前で描く必要がある）
