# マイルストーン 2: OpenArm v2 による両腕の持ち替え

2026-11-12 開始。根拠は `docs/openarm_spike.md`（下見）。マイルストーン 1（SO-101）と同じ作り方で進める: 物理は MuJoCo、それ以外は自作。シードで全てが決まる。特権エキスパートから BC と DAgger で学習し、ブラウザで閉ループのデモを動かす。

## 方針

- **SO-101 側は壊さない。** OpenArm 用のコードは `keiarm/openarm/` に置き、公開中のデモと評価結果はそのまま保つ。共通化は、2 台目のロボットで同じものが本当に要ると分かった箇所だけ行う（先回りして抽象化しない）
- ロボットは `third_party/openarm_v2/`（編集禁止）。シーンは `MjSpec` で組み、timestep・重力補償・材質はそこで上書きする
- 見た目は単純に（影・反射なし、単色）。台座は Enactic の衝突用メッシュを見た目にも使う。16 万面の見た目用メッシュは使わない

## 固定する値（Phase 0 で確定）

| 項目 | 値 |

## 最初のタスク: 棒を持ち替えて置く（Phase 1 で立方体から変更）

右手側に置かれた棒を右手で取る。中央の空中で左手に渡し、左手側の皿に置く。棒は片腕では届かない位置に出すので、持ち替えないと解けない。

- **物体は棒**（断面 2.5–3.5 × 2.5–4 cm、長さ 15–18 cm。Phase 2 で 13–16 cm から延長）。当初は 5 cm の立方体の予定だった。しかし両手が同時に上から掴むには、指先の中点を 9–10 cm 離す必要がある（8 cm では腕どうしの隙間が 3 mm、10 cm で 23 mm）。そのため利用者の判断で棒に変えた（2026-11-12）
- 掴む点: 右手は棒の中心から −y 側に 6 cm、左手は +y 側に 6 cm（`BAR_GRIP_OFFSET`。Phase 2 で 5 cm から変更）。右手の把持が中心寄りにずれたら、左手はその分外側を掴み、手の間隔を 11.5 cm 以上に保つ。どちらも真上から掴み、顎は棒を横切る向きに閉じる。把持の向きは手ごとの「自然な」向きだけ
- 棒の出現範囲: 右手の掴む点が右の扇形（半径 0.21–0.27 m、方位 −65°〜−10°）の中にあり、棒の向きは y 軸から −20°〜+45°（Phase 2 で ±45° から変更）、棒全体が机の手前縁から 4 cm 以上内側にある
- 皿の出現範囲: 左手の置く点（皿の中心 + (0, 5 cm)。棒は y 軸向きに置く）が左の扇形の中にある。皿の半径は 7–9 cm
- 受け渡しの位置: x 0.25–0.30 m、y = 0、高さ 10–20 cm で両腕とも IK が解け、腕どうしの隙間は 23 mm ある（指先の中点の間隔が 10 cm のとき）
- 成功の条件（Phase 2–3 で確定）: 棒の中心が皿の上で静止し、どちらの指も触れていない状態が 10 ステップ続く
- 左右反転（左から右へ）は後回し

## 評価ハーネス（Phase 3 で確定）

`keiarm/openarm/eval.py`、入口は `scripts/eval_openarm.py`。SO-101 の `keiarm/eval.py` と同じ形にし、SO-101 側は変えていない。

- **段階**（`task.STAGES`）: 右手が接近 → 右手で把持 → 持ち上げ → 両手で保持 → 左手だけで保持 → 皿の上 → 完了。エピソードごとに最遠の段階と、各段階に初めて着いたステップを記録する
- **違反**: 腕どうしの接触（ステップ数）、腕と机の 20 N 超の衝突、棒の落下、棒が机の外へ出た
  - 落下の定義: 持ち上げて保持していた棒に、**どの指も 3 ステップ続けて触れていない**。ただし皿の上の低い位置で離した場合は除く。搬送中は片方の指の接触が 1 ステップ途切れることがあり、「両指で保持していない」を落下とすると、成功したエピソードの 6% で誤検出した
- **失敗の分類**（最遠の段階で決める）: 右手の掴み損ね / 持ち上げ失敗 / 受け渡し失敗 / 右手が離せない / 左手の搬送失敗 / 置き損ね / 落下（持ち上げ・左手の搬送の段階で落とした）/ 棒が机の外へ。失敗したエピソードは、最終状態からエキスパートに 450 ステップ任せて完了できるかも調べる（「方策の迷い」か「詰んでいる」かの区別）
- **外乱スイート**: 1 エピソードに 1 回。内容と時刻はシード（`episode_rng` の系列 2）と段階で決まる。実際に起きたステップを記録し、再生（`eval.replay`）ではそのステップに適用する

| 外乱 | いつ | 何を |
|---|---|---|
| `move` | 10〜39 ステップ目（右手が閉じる前） | 棒を右側の出現範囲の別の場所へ。向かっていた掴む点から 4 cm 以上離す |
| `knock` | 「持ち上げ」に着いてから 5〜29 ステップ後 | 棒を右側の出現範囲へ落とす（右手が掴み直す） |
| `drop` | 「左手だけで保持」に着いてから 0〜19 ステップ後 | 棒を右側の出現範囲へ落とす（受け渡しからやり直し） |
| `plate` | 「左手だけで保持」に着いてから 0〜19 ステップ後 | 皿を左側の出現範囲の別の場所へ（5 cm 以上離す） |

- 当初は「棒を左側へ移し、左手だけで置かせる」外乱も考えた。しかし左手の届く範囲の大半を皿が占めるため、皿と重ならない置き方はシーンによって 0〜50% しかなく、多くのシーンで成り立たなかった。代わりに `drop` を入れ、外乱が全段階（把持前、持ち上げ後、受け渡し後、搬送中の皿）を覆うようにした
- 方策の入口は `keiarm/openarm/policies.py`（`expert`、`expert-noisy:<σ>`、基準線の `hold` と `freeze`）。結果は `runs/eval/openarm_*/episodes.json` に出すので、`scripts/compare.py` で比べられる

## ブラウザ（Phase 4 で確定）

- 書き出し: `scripts/export_web_openarm.py` → `web/public/openarm_scenes/`（シーン JSON）と `web/public/assets/openarm/`（メッシュ）。どちらも生成物で git 管理外
- 見た目用メッシュは 25% に間引く（頂点を結合してから）。物理は変わらない（ボディの慣性は `<inertial>` で明示、見た目用ジオムは衝突しない。テストでビット一致を確認）
- `web/src/openarm/sim.js` は `scene.reset_data`、`env.teleport_bar` / `move_plate`、`task.is_success` を写したもの。Python 側を変えたら両方直す。定数は JSON の `constants`
- 描画は SO-101 と共通の `web/src/render.js`。クリップ面は MuJoCo と同じ `vis.map.znear/zfar × stat.extent`（手首カメラの直前にグリッパーの筐体がある）
- 確認: `npm --prefix web test`（Node で再生）、`uv run python tools/browser_check_openarm.py [--gpu]`（ヘッドレス Chrome）

## ブラウザ推論（Phase 7）

- モデル: `scripts/export_onnx.py --robot openarm --run oa_r1` → `web/public/models/openarm.{onnx,json}`（47.2 MB、PyTorch との差 1.7e-5）。`web/src/policy.js` / `policy_worker.js` は次元を `meta.action_dim` から受け取る（SO-101 は 6 のまま）
- ページ: `web/openarm.html`（公開先では `/keiarm/openarm.html`）。SO-101 のページと相互にリンク。モード「モデル / エキスパート」、棒と皿をドラッグで動かせる
- `web/src/openarm/sim.js` に段階の判定（`task.stage_of` の写し）と外乱の発火（`eval.py` の Monitor と同じ「段階に着いてから delay ステップ後」）を加えた。Node の再生で、段階に着くステップの差は最大 1、外乱の発火ステップは全て一致
- 閉ループ評価: `tools/browser_eval_openarm.py --gpu --python-run openarm_keigrasp-oa_r1_eval3 [--disturb suite]`（シミュレーションは推論を待つ同期実行）。実時間の確認: `tools/browser_demo_check_openarm.py --gpu [--url ...]`
- 推論は onnxruntime-web の WASM（1 スレッド）で約 180 ms。10 ステップ（333 ms）に 1 回なので実時間に間に合う。ヘッドレス Chrome には WebGPU のアダプタが無く、強制すると CPU のエミュレーションになり遅い
